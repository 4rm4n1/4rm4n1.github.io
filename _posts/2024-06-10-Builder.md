# Intro

`Builder` es una máquina de dificultad media de la plataforma `Hack The Box` que gira en torno a una instalación expuesta de `Jenkins`.  El camino de compromiso comienza con la explotación del `CVE-2024-23897`, una vulnerabilidad crítica que permite leer ficheros del servidor. Abusando de este fallo, podemos extraer el hash de la contraseña de un usuario de `Jenkins` crackearlo y acceder al panel de administración.
Una vez dentro, la `Script Console de Jenkins` nos permite ejecutar comandos directamente en el servidor. Desde ahí descubrimos que `Jenkins` almacena una clave privada SSH del usuario `root` entre sus credenciales. Usando el propio `Jenkins` para descifrarla, obtenemos acceso completo a la máquina como root a través de SSH.
Esta máquina es un ejemplo muy representativo de algo que ocurre en entornos reales: una sola aplicación mal configurada y sin actualizar puede comprometer por completo un servidor, incluso cuando el resto del sistema está perfectamente securizado.

## CVE-2024-23897 

Una simple búsqueda en google de `jenkins 2.441` revela que esta versión es vulnerable al [CVE-2024-23897](https://www.incibe.es/incibe-cert/alerta-temprana/vulnerabilidades/cve-2024-23897)  una vulnerabilidad crítica de lectura arbitraria de ficheros en el servidor. En el siguiente enlace [sonarsource](https://www.sonarsource.com/blog/excessive-expansion-uncovering-critical-security-vulnerabilities-in-jenkins/?utm_medium=social&utm_source=twitter&utm_campaign=research&utm_content=blog-excessive-expansion-uncovering-critical-security-vulnerabilities-in-jenkins-240125-p1) encontramos la explicación detallada de la vulnerabilidad para poder entenderla . 

**¿Cómo funciona?**

`Jenkins` expone una interfaz de línea de comandos llamada `jenkins-cli` en la ruta `http://server:port/jnlpJars/jenkins-cli.jar`. Internamente esta CLI utiliza la librería Java `args4j` para parsear los argumentos que recibe. Esta librería tiene una funcionalidad que permite referenciar el contenido de un fichero usando el carácter `@`, por ejemplo `@/etc/passwd` le diría al parser `lee el contenido de este fichero e inyéctalo como argumento`. El problema es que `Jenkins` no desactiva esta funcionalidad, lo que permite a un atacante (incluso sin estar autenticado) pasarle a la CLI una ruta de fichero arbitrario del servidor y obtener su contenido en la respuesta. Dependiendo de qué ficheros sean legibles, esto puede escalar desde un simple `information disclosure` hasta ejecución remota de código, por ejemplo leyendo claves privadas SSH o credenciales. 

En el siguiente repositorio encontramos un `PoC` para explotar esta vulnerabilidad [Maalfer](https://github.com/Maalfer/CVE-2024-23897) . Vemos como primero obtiene el cliente CLI expuesto en la ruta y luego invoca el CLI con el comando `connect-node`, es ahí donde en vez de pasarle un nombre de nodo legítimo le pasamos la ruta `@{ruta}` con la ruta que elijamos. Para ejecutar el PoC es necesario tener Java instalado en la máquina atacante, ya que el payload lanza `java -jar jenkins-cli.jar`. Sin Java, el script descargará el `.jar` correctamente pero fallará en el segundo paso.

```bash
❯ python3 exploit.py 10.129.230.220 8080 /etc/passwd
```

![img](assets/builder/build4.png)

El resultado confirma dos usuarios, `root` con su directorio en `/root` como es habitual y `jenkins` un usuario del sistema con su home asignado en `/var/jenkins_home` que podemos intuir que es donde esta la raíz de la aplicación. Con una simple búsqueda en Google como `Jenkins home directory structure` o `jenkins credentials file location` podemos ver como jenkins organiza sus ficheros. Ahora el proceso de razonamiento que seguimos después de investigar y ver como organiza Jenkins los directorios es el siguiente:

1. `/etc/passwd`: nos dice que el home del usuario `jenkins` es `/var/jenkins_home`
2. Buscamos en Google, descubrimos que `Jenkins` guarda los usuarios en `[jenkins_home]/users`
3. Leemos `users.xml` obtenemos el nombre exacto de la carpeta de `jennifer`
4. Leemos el `config.xml` obtenemos el hash de su contraseña

```bash
❯ python3 exploit.py 10.129.230.220 8080 /var/jenkins_home/users/users.xml
```

# Shell as root 

## Enumeración de `/var/jenkins_home`

Enumerando el directorio de mi usuario encontramos el fichero `credentials.xml`

![img](assets/builder/build10.png)

El fichero contiene una clave SSH del usuario `root` almacenada directamente en texto dentro del XML lo que `Jenkins` llama `DirectEntryPrivateKeySource`. La clave está cifrada con el cifrado interno de `Jenkins`, por lo que necesitaremos descifrarla antes de poder usarla. `Jenkins` permite almacenar credenciales SSH para conectarse a otros servidores desde los pipelines. El problema es que esas credenciales quedan guardadas en `credentials.xml` y cualquiera que pueda leer ese fichero puede obtenerlas. En este caso la clave pertenece a `root`, lo que nos abre la puerta a la escalda de privliegios completa. Ahora realizando una búsqueda en Google para descifrar la clave SSH, en el primer resultado nos proporciona directamente el snippet Groovy necesario

![img](assets/builder/build11.png)

Lo ejecutamos y obtenemos la clave SSH de root descifrada, nos la copiamos a nuestra máquina de atacante y la asignamos los permisos `chmod 600 id_rsa`

![img](assets/builder/build12.png)

Nos conectamos a la máquina como `root`.

