____

`Codify` es una máquina Linux de dificultad `Easy` de la plataforma `Hack The Box`. Gira en torno a una aplicación web que permite ejecutar código `JavaScript` de forma online. La superficie de ataque inicial es una versión vulnerable de la librería `vm2` que permite escapar del entorno asilado de ejecución y obtener ejecución remota de comandos en el servidor. Una vez dentro descubrimos una base de datos `SQLite` con credenciales hasheadas de un usuario activo de la máquina que crackeamos con `hashcat` para acceder por SSH al host. La escalda final se consigue tras analizar un script que este usuario puede ejecutar con permisos de `root`.

![img](assets/codify/co1.png)

Explorando los distintos directorios de la web podemos ver en `/about` que la aplicación usa la librería `vm2 3.9.16` para aislar y ejecutar el código de los usuarios de forma segura. 

![img](assets/codify/c02.png)

![img](assets/codify/co3.png)

`Vm2` es una librearía de `Node.js` que crea un `sandbox`, es decir un entorno aislado donde se supone que el código del usuario se ejecuta sin poder acceder al sistema real desde donde se sirve. El problema es que si esa caja tiene agujeros un atacante puede escapar de ella y ejecutar comandos directamente en el servidor. Una búsqueda rápida revela que `vm2 3.9.16` es vulnerable a una escapada de sandbox que permite ejecución remota de comandos. Esto significa que puedo enviar código `JavaScript` malicioso al editor y, en lugar de quedarse confinado en la `sandbox`, escapar y ejecutar comandos en el servidor. 

![img](assets/codify/co4.png)

Si accedemos al primer enlace encontramos una prueba de concepto `PoC` pública lista para usar, copiamos el payload y lo pegamos directamente en el editor de código de la web, modificando el comando embebido por `id` para verificar que tengo ejecución de código en el servidor. 

![img](assets/codify/co5.png)

Ahora modificamos el comando para mandarnos una revershell a nuestra máquina de atacante, con el siguiente payload:

Los permisos están bien configurados por lo que descartamos la idea de sustituir el script por uno malicioso propio. El siguiente paso es leer el contenido del script y ver cual es su función. Analizando el script hay dos fallos graves de seguridad en el código. 

![img](assets/codify/co6.png)

El primero está en la línea 9. El problema esta en que `$USER_PASS` no está entre comillas. En Bash cuando se usa `[[ ]]` y el lado derecho de una comparación == no está entrecomillado, Bash no lo trata como texto literal sino como un patrón global.   

```bash
if [[ $DB_PASS == $USER_PASS ]]; then
```

Esto significa que si introducimos `*` como contraseña, la comparación se convierte en: 

```bash
if [[ $DB_PASS == * ]]; then
```

Y `*` es un patrón global que significa `cualquier cosa`, por lo que  la comparación nos devuelve un `True` ya que siempre será verdadera. El código escrito correctamente sería:

```bash
if [[ $DB_PASS == "$USER_PASS" ]]; then
```

Con las comillas Bash trata `$USER_PASS` siempre como texto literal, por lo que si el usuario introduce un `*` como contraseña lo compara exactamente contra el `asterisco` y no contra `cualquier cosa`.  El segundo fallo es leer la contraseña de `root`en la línea 3 y pasarla directamente como argumento en la línea de comandos mediante la flag `-p$DB_PASS`. En Linux, cualquier usuario del sistema puede ejecutar `ps aux` en el momento que un proceso este corriendo y ver todos sus argumentos, por lo que podemos leer dos veces la contraseña que pasa guardada en `/root/.creds`. 

Subimos a la máquina la herramienta `pspy64` y la ejecutamos antes de ejecutar el script. 

```bash
❯ scp pspy64 joshua@10.129.22.21:/tmp
joshua@10.129.22.21's password: 
pspy64       
```

Ejecutamos el script y cuando nos pida la password introducimos un `*`.
